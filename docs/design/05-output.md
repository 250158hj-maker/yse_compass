## 5-4. 生成手段の方式（蒲山の技術検証・決着）

**決定（2026-09-04）：サーバーサイド生成。ヘッドレスブラウザは使わず、純粋 JS の PDF ライブラリ（`@react-pdf/renderer` 相当）で組む。** `decisions.md` 参照。

### 比較した3案

| 案 | 実現方法 | 検証結果 |
| --- | --- | --- |
| A. サーバー生成（ヘッドレスブラウザ） | Puppeteer/Playwright ＋ Chromium で HTML→PDF | **コスト大。不採用。** Alpine ベースの Docker イメージに Chromium を追加すると **235MB → 1.35GB（+1.1GB、195パッケージ）** に膨張することを実測。`--no-sandbox` 起動フラグ・フォントパッケージ別途導入・プロセスごとのメモリ消費など運用の複雑さも増える |
| B. サーバー生成（純粋 JS PDF ライブラリ） | `@react-pdf/renderer` 等、Chromium を介さず PDF バイト列を直接組み立てるライブラリ | **採用。** ローカルで実機検証：2ページの日本語 PDF を **126ms・出力72KB** で生成。日本語フォント（Noto Sans JP）はサブセット埋め込みが自動で行われ、追加の実行環境（ブラウザ・ネイティブ依存）が不要。依存パッケージも軽量（60パッケージ程度） |
| C. 印刷用ビュー＋ブラウザ印刷 | 専用ページを `@media print` で組み、先生がブラウザの印刷機能で PDF 保存 | 実装コストは最小だが、**先生の手動操作（印刷ダイアログ→PDF保存）が生成の都度必要**で、`../requirements.md` §3-3 の「生成すると…概要集 PDF が得られ」という受け入れ基準に対して一手余分になる。ブラウザ間のページ割り差異のリスクも残る |

### 採用理由

- **「安いほうを選んでよい」の基準（`../open-questions.md` §6）に照らすと、A（ヘッドレスブラウザ）が最もコストが高く、Bが最も低い。** Chromium 同梱によるイメージサイズ・運用複雑さの増大は、概要集という**1種類・低頻度**の出力物には見合わない
- **C（印刷ビュー）よりも B を優先する。** 受け入れ基準「生成すると PDF が得られる」を one-click のダウンロードで満たせ、Cのような手動印刷操作を要求しない。実装コストは C とほぼ同水準（新規の重い依存が無い点は共通）で、UX が上回る
- レイアウトは「システム定義の統一レイアウト（コード定義・1種類）」（`../requirements.md` §3-3）と決まっており、任意の Web ページを丸ごと PDF 化する自由度（A の強み）は要らない。**固定レイアウトを直接組み立てる B の設計と要件が一致する**
