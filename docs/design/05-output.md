## 5-4. 生成手段の方式（蒲山の技術検証・決着）

**決定（2026-09-04）：サーバーサイド生成。ヘッドレスブラウザは使わず、純粋 JS の PDF ライブラリ（`@react-pdf/renderer` 相当）で組む。** `decisions.md` 参照。

### 比較した3案

| 案 | 実現方法 | 検証結果 |
| --- | --- | --- |
| A. サーバー生成（ヘッドレスブラウザ） | Puppeteer/Playwright ＋ Chromium で HTML→PDF | **コスト大。不採用。** Alpine ベースの Docker イメージ（`node:24-alpine`。**計測当時の** 8-1 開発環境と同一ベース。下記「前提の変化」）に Chromium を追加すると **235MB → 1.35GB（+1.1GB、195パッケージ）** に膨張することを実測。`--no-sandbox` 起動フラグ・フォントパッケージ別途導入・プロセスごとのメモリ消費など運用の複雑さも増える |
| B. サーバー生成（純粋 JS PDF ライブラリ） | `@react-pdf/renderer` 等、Chromium を介さず PDF バイト列を直接組み立てるライブラリ | **採用。** ローカルで実機検証：日本語2ページ（各ページ見出し1行＋本文2行程度の簡易データ）の PDF を **126ms・出力72KB** で生成。日本語フォント（Noto Sans JP・元ファイル16MB）はサブセット埋め込みが自動で行われ、追加の実行環境（ブラウザ・ネイティブ依存）が不要。依存パッケージも軽量（60パッケージ程度） |
| C. 印刷用ビュー＋ブラウザ印刷 | 専用ページを `@media print` で組み、先生がブラウザの印刷機能で PDF 保存 | 実装コストは最小だが、**先生の手動操作（印刷ダイアログ→PDF保存）が生成の都度必要**で、`../requirements.md` §3-3 の「生成すると…概要集 PDF が得られ」という受け入れ基準に対して一手余分になる。ブラウザ間のページ割り差異のリスクも残る |

> **計測条件**：ホスト OS は Docker Desktop 上の Linux コンテナ（`node:24-alpine`／`postgres:16-alpine` を使う**計測当時（2026-09-04）の**本リポジトリの開発環境と同条件）。A の比較対象イメージは `node:24-alpine` に `apk add chromium` を追加しただけの最小構成（puppeteer-core 等のインストールは環境要因で計測未了。**イメージサイズの膨張はパッケージ追加単体の実測値**）。B は概要2件分のダミーデータでの単発計測で、本番相当のページ数（発表チーム数）での再計測はしていない

> [!warning] **前提の変化 — A 案の却下根拠は、いまのリポジトリに存在しない指標を測っている**
> 本検証の直後に **F-02 が決着**し、**Docker で管理するのは PostgreSQL のみ・Next.js アプリはホスト直起動**になった（`../decisions.md` 2026-09-04・`08-architecture.md` 8-1。`Dockerfile` は削除済み）。したがって **235MB→1.35GB が記述する開発イメージは、もう存在しない。** 本番側は 8-7（デプロイ構成）保留のため、まだ測れない。
> **結論（ヘッドレス非依存）は変えない。** 下の採用理由のうち **3 点目は実行環境に依存しない**ため、根拠の重心はそこにある。
> ただし **ホスト直起動で A 案を採った場合のコスト**（開発者ごとに Chromium 実行環境を用意する）は**測っていない**。8-7 決着時に、本番イメージのコストとあわせて読み直すこと。

### 採用理由

- **`../requirements.md` §3-3 の受け入れ基準は生成手段を縛っていない**（手段の選択は設計側の裁量）。したがってコストで選んでよく、A（ヘッドレスブラウザ）が最も高く B が最も低い。Chromium を**実行環境に持ち込むこと**による増大（イメージサイズ・`--no-sandbox` 起動フラグ・フォントの別途導入・プロセスあたりのメモリ）は、概要集という**1種類・低頻度**の出力物には見合わない。**この増大は梱包形態（コンテナかホスト直か）に依らない**
- **C（印刷ビュー）よりも B を優先する。** 受け入れ基準「生成すると PDF が得られる」を one-click のダウンロードで満たせ、Cのような手動印刷操作を要求しない。実装コストは C とほぼ同水準（新規の重い依存が無い点は共通）で、UX が上回る
- レイアウトは「システム定義の統一レイアウト（コード定義・1種類）」（`../requirements.md` §3-3）と決まっており、任意の Web ページを丸ごと PDF 化する自由度（A の強み）は要らない。**固定レイアウトを直接組み立てる B の設計と要件が一致する**
- **実測は計測当時の開発イメージでの検証で、その構成は F-02 で解消された**（上記「前提の変化」）。本番相当のイメージでのコストは 8-7（デプロイ構成）保留のためまだ測れない。結論（ヘッドレス非依存を選ぶ）は禁則5（未決の上ではフォールバックで作る）に沿った暫定選定であり、**8-7 決着時に前提として読み直すこと**
