## 10-2. 先生ホワイトリストの 1 人目の入れ方 — DB への 1 回限りの直接投入

**対応要件**：`../requirements.md` §3-6（2026-09-06 確定）
**設計判断の出典**：`../decisions.md` 2026-09-06（H-11 の決着）。**規則の本文は再掲しない**（`../../AGENTS.md` 禁則2）。
**本節の境界**：1 人目の投入の対象・行の形・主体・環境。2 人目以降は SC-20（`04-screen.md`）、クラス・チーム・年度の初期データは 10-1。

### 要件との対応

| 規則（`../requirements.md` §3-6・`../decisions.md` 2026-09-06） | 本節での実現 |
| --- | --- |
| 1 人目は運用開始時に DB へ直接投入する（1 回限り） | 下の「投入する行」を、運用開始時に 1 度だけ DB へ入れる。投入のための画面・コード上の昇格の仕組みは作らない |
| 投入するのは「運営を回す人」（「スーパーユーザー」という語は使わない） | 卒業制作運営の実務担当の先生 1 人 |
| 以後の追加は SC-20 のみ。ホワイトリストを空にできない（自分自身のロールは解除できない） | 再投入は要らない。**本番で投入する人が誰になっても、この不変条件で本節は成立する**（決定の根拠③） |

### 投入する行

`users` の 1 行。`role` は `'teacher'`（`06-data.md` 6-3 の `users`。`id`・`role` は確定の範囲）。`email` は学校 Workspace ドメインのアカウント、`name` は NOT NULL なので値が要る。

- **`email`・`name` は 06 の確定の範囲外**（`email` を一意キーとすることは `../decisions.md` 2026-11-06 の H-32 の行で決着。`name` は H-26）。列名・NULL 可否が変わりうるので、06 の現行の定義に従い、06 が変わったら本節を直す。
- **照合は 7-2 の `jwt` コールバックが `users` を `email` で引く。** 実装の事実として（正典ではない）、`email` が Google の返す表記と大文字小文字まで違うと、別の行が作られて先生が生徒として扱われる（`src/lib/auth/callbacks.ts`・`scripts/seed-dev.mjs` のコメント）。
- **行が既にあれば `role` を `teacher` に更新し、無ければ行を入れる。** 当人がすでにサインインしていると、初回サインインで生徒の行が作られていて、`email` は UNIQUE なので単純な追加は一意違反になる（実装の事実。`src/lib/auth/callbacks.ts` の `findOrCreateUser`、`scripts/seed-dev.mjs` の `ON CONFLICT (email) DO UPDATE SET role`）。
- ロールはサインイン時にトークンへ載る（7-2・H-30）。**サインイン済みだった人は、更新のあとにサインインし直す。**

### 誰が・どこへ入れるか

| --- | --- | --- |
| 開発 | 各開発者 | `scripts/seed-dev.mjs`（`pnpm db:seed`）が `DEV_TEACHER_EMAIL` の先生を入れる。ローカルの DB 以外には流さない。**本番の手順ではない** |
| デモ（2026-12-18） | デモサーバーの持ち主 | `pm/demo-server.md` の seed の手順。**本番の手順ではない** |
