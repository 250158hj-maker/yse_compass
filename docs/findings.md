## このファイルの使い方

**実装中に気づいたことを、その場で書き留めるだけにする。** 分類・優先度づけ・要件への反映は**別の回で行う**。

> 作りながら分析すると、分析に引きずられて実装が「想定した穴の確認作業」になり、**想定外の発見が出なくなる。記録と分析を時間で分離する。**

- 「実装しようとしたら決まっていなかった」ものは、**ここに書いたうえで `open-questions.md` にも 1 件立てる**（`CLAUDE.md` 禁則1）
- 環境構築で詰まっただけのもの（バージョン・ツールの設定など）は**書かない**。それは設計の発見ではない
- **決着しても行を削除しない。** 決着日と `decisions.md` への反映を追記する（決定の履歴を消さないのと同じ思想）

### 記録のフォーマット

```
### F-xx  <1行の問い>

- ref   : requirements.md / glossary.md のどこに効くか
- steps : どの作業・どの画面で出たか
- what  : 実装しようとして何が起きたか
- why   : なぜ決めきれないか（両方の選択肢に理があること）
- 決着  : （未決着なら空欄。決着したら日付と decisions.md への反映）
```

`why` に**両方の選択肢の理**を書けないものは、たいてい発見ではなく好みである。書けるかどうかで選別する。

- ref   : `../CLAUDE.md` §5（技術構成の ORM 行）／`design/08-architecture.md` 8-1
- steps : 08 方式設計（8-1 技術スタック）を書くために既存実装を確認した際、`src/app/api/health/db/route.ts`（DB 疎通確認エンドポイント、`main` に存在）が `pg` の `Pool` を直接使っているのを確認。`package.json` に Prisma 系パッケージは無い。**この乖離自体は 2026-09-03 の三者整合性監査で M-1 として既に見つかっていたが、`open-questions.md` への起票が漏れていた。** 08 執筆時に実物を再確認し、未決 ID（H-17）へ正式に昇格させた
