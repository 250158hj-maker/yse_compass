## 2. 運営の骨格

### 年度

運営の最大単位。「2026年度卒業制作」のように年度で括る。

- 先生の「**年度を開始**」操作（＝年度一括セットアップ）で始まり、「**年度をアーカイブ**」操作で運営動線から外れる。**アーカイブは可逆**（2026-07-26）
- 年度セットアップは 4 発表会＋定番の資料枠構成の骨組みを**一括生成**する。これが発表会作成の**正規入口**であり、任意個数・任意種別の作成は持たない（2026-07-24）
- **確定（2026-09-04・H-9 決着）**：年度セットアップと**チーム登録は独立した操作**で、**順序を強制しない**。チームが 0 件のときの提出状況一覧は空状態を表示する

### 発表会

年度に **4 回**。先生が作成・編集する**運用データ**であり、コードに焼き込む固定データではない（2026-07-24）。

- **回種別**：`企画 / 設計 / 試作 / 最終` の**固定 4 種・順序つきの列挙**。順序性は一覧・概要集・アーカイブの文脈表示に使う（2026-07-24）
- 日程・資料枠は生成後に個別編集できる
- **公開状態**を持つ。公開は先生の明示操作（公開ボタン）による**発表会単位の一括公開**（2026-07-26）
- **発表順**（後述）と時刻枠を束ねたタイムテーブルを持つ

### 資料枠

「何をいつまでに準備すべきか」の定義。発表会がこれを複数持ち、生徒には提出対象として表示される。

| 属性 | 状態 | 出典 |
| --- | --- | --- |
| 種類（名称） | 確定 | 2026-07-24 |
| 締切 | 確定（**ソフトデッドライン** — 超過しても提出できる） | 2026-07-26 |
| テンプレート参照（リンク・任意） | 確定 | 2026-07-24 |
| **必須／任意の区別** | 確定 | 2026-08-18 ヒヤリング回答 |
| **提出方式（参照登録／フォーム入力）** | 確定：概要枠のみフォーム入力・他はリンク登録 | 2026-09-04（H-2 決着） |

- 定番の資料枠構成（4 発表会それぞれの中身）は**コード定義**で持つ。プリセット管理 UI は作らない（2026-07-24）。実像は `hearing.md` を参照
- **確定（2026-09-04・H-2 決着）**：概要枠のみフォーム入力、他はリンク登録。提出方式を資料枠の汎用属性としては持たず、概要を独立エンティティとして扱う。過去スパイクの `kind: "form" | "link"` は採らない
- **未決（H-13）**：Drive 統合を採用した場合、同じ資料枠に「Drive 配置による提出」と「外部 URL 登録による提出」（Canva・動画）が**混在する**。分岐が 1 段深くなる可能性がある

## 3. 人・組織

### クラス

**AI21 / BD21 / GS21 / IG21 / IG22** の 5 つ（2026-08-19 分析で ER 上の実在単位と確認）。

効く箇所は 3 つ。

1. Drive のディレクトリ構成（年度 → 工業2年 → 卒業制作 → 番号_発表名 → **クラス略称**）
2. 提出状況一覧のフィルタ（`requirements.md` §3-2）
3. 先生ロールの表示既定値

**命名は「学科＋学年＋組」の合成**（例：`IG21` ＝ IG 科 2 年 1 組）。卒業制作は 2 年次のみなので学年は常に `2`。組数は学科によって異なる（IG 科のみ 2 組）。

- **確定（2026-09-04・H-3 決着）**：クラスは**年度セットアップで生成する運用データ**で、登録主体は先生。**クラス名は分解せず文字列 1 つ**で持つ（学科・学年・組へ分解することを要求する要件が正典に無い）

### チーム

卒業制作の制作単位。作品を 1 つ持つ。

- **確定（2026-09-04・#6 決着）**：**先生（担任）が作成する。生徒はチームを作成できない**（材料：2 年次 1 学期に決定し、現在はスプレッドシートで管理 — 2026-08-18 ヒヤリング回答）
- クラスに属する
- **リーダー**（チーム代表者）を 1 名持つ

### リーダー（チーム代表者）

**公開許可の同意者**。この役割のために ER 上でリーダー概念が必要なことは確定している（2026-07-26）。

- **確定（2026-09-04）**：**チームの属性**（代表者 1 名への参照）として持つ。**ロールではない** — ロールが DB で持つ値は「先生／生徒」の 2 値のまま（§3 ユーザーとロール）
- **確定（2026-09-04）**：責務は**公開許可の設定のみ**で、他の権限を持たない。割り当てはチーム作成時に**先生が 1 名指定**し、以後変更できる（先生の代理設定は 2026-07-26 で決定済み）

### ユーザーとロール

- ロールが DB で持つ値は「**先生／生徒**」の 2 値で足りる
- 「発表する生徒」「聴く生徒」は**ロールではなく文脈** — その発表が自チームか否かで決まる。ここを混同すると認可設計が肥大する
- **未決（H-10）**：サインインしたユーザーが**先生か生徒かを何で判定するか**が未定義（Workspace のグループ／メールアドレスのパターン／手動登録）。「OAuth が通るか」よりも手前の問題
- **未決（H-11）**：**最初のスーパーユーザー**がどこから生まれるかが未定義（年度セットアップにはスーパーユーザーが要り、スーパーユーザーを作るにはセットアップが要る）
- **未決（#8）**：先生ロールの**親子二層構造**の要否（冨永先生の要望）

## 4. 提出とその周辺

### 発表

**チーム × 発表会**。1 回の発表という出来事そのもの。

**コメント・いいねのアンカーはこの粒度**（2026-07-24）。資料が差し替えられても、リンクが変わっても、コメントの対象がずれないようにするための安定エンティティ。

- **発表順**（整数）を持つ

### 提出

**チーム × 発表会 × 資料枠**。

- 状態は「**未提出／提出済み**」の **2 値**。完了定義は提出フォーム完了時点（2026-07-24）
- 差し替えは**上書き**。**版履歴を持たない**（2026-07-24）
- 差し替えの終端は**年度アーカイブ**。それ以降は編集できない（2026-07-26）
- URL は**形式検証のみ**行う。アクセス可否は検証しない（2026-07-26）
- 「リンクはあるが開けない」等の権限状態を**状態値として持たない**

### 遅延

**状態ではなく導出値。** 提出日時と締切の比較で導かれる表示であり、第 3 の状態ではない（2026-07-26）。

- **未決（H-6・ER 直結）**：差し替えが上書きで提出日時が単一フィールドの場合、**初回提出日時が失われる**。締切前にきちんと提出したチームが後日差し替えると、**遅延として表示されてしまう**。差し替え可能期間は年度アーカイブまで（数か月）あるため稀ではない

### 発表順

**発表が持つ整数属性。** 次の 4 つがこれに依存している。

| 依存元 | 依存の内容 |
| --- | --- |
| 概要集 | 発表順に束ねて PDF を生成する |
| タイムテーブル | 発表順と時刻枠を持つ |
| 現行の Drive 運用 | ファイル名に発表順番号が埋まっている |
| Drive 統合（未決#10） | 「発表順とファイル名の同期からの解放」が価値仮説 |

- **確定（2026-09-04・H-5 決着）**：発表順の決定操作はタイムテーブル編集（§3-10）に属する。並び替えが発表順の決定であり専用画面は設けない。発表順は発表エンティティの整数属性として持つ。順番変更は「ほぼ毎回」起きる（2026-07-28 回答）主要導線

## 5. 概要と概要集 — **別の語**

**この 2 語は必ず区別すること。** 混同すると生徒の画面に「概要集を提出する」と表示され、それは嘘になる（生徒が提出するのは概要であって概要集ではない）。

| 語 | 何か | 誰が作るか |
| --- | --- | --- |
| **概要** | 生徒が**構造化フォームで入力する提出物**。1 チーム × 1 発表会（年 4 件） | 生徒 |
| **概要集** | システムが概要を**発表順に束ねて生成する PDF** | システム（先生が生成操作） |

### 概要

- 構造化データ。入力欄は評価観点（背景・動機／起・結／1 ページ集約）を焼き込む（2026-07-26）
- **使用技術欄**を持つ。これが**アーカイブ検索の対象**であり、独立したタグ機能の代替（2026-07-26）
- 資料枠のうち**概要枠だけがフォーム入力**で、他はリンク登録（`requirements.md` §3-4 の唯一の例外）
- **未決（T-3）**：使用技術欄が自由記述だと検索精度が出ない（React / react / React.js）。現行テンプレは開発環境・開発言語・操作環境の 3 欄

### 概要集

- レイアウトはシステムが定義する **1 種類のみ**（コード定義・編集 UI なし）
- いつでも何度でも生成できる。未提出チームがあれば警告し、了承でスキップして生成する
- **確定（2026-09-04・H-1 決着）**：資料枠名は「概要」。「概要集」は生成物（PDF）の名前として予約する。現行運用の呼称「概要集（Word）」は `hearing.md` §7-2 に原文のまま残す
- **未決（H-7・H-8）**：締切がソフトデッドラインである以上「生成 → 遅れて提出が届く」が普通に起き、発表順は「ほぼ毎回」変わる。**生成済み概要集が構造的に陳腐化する**が、再生成・再公開の関係が定義されていない。概要集は校外配付物なので、載っていないチームが出るのは事故になる

## 6. 蓄積

### 作品

**チーム × 年度**。4 回の発表を貫く「その年度にそのチームが作ったもの」。

**公開許可の単位**（2026-07-26）。「一部の資料だけでは卒業制作の蓄積にならない」ため、発表単位ではなく作品単位で許可を取る。

### 公開許可

- 単位＝**作品**／同意者＝**チーム代表者（リーダー）**／時期＝**全発表会終了後**（在校中に取り切る）／既定＝**非表示**（2026-07-26）
- 代表者がシステム内で設定し、先生が状況確認・**代理設定**できる
- **これは「アーカイブでの表示」への同意であって、データ削除請求の手段ではない。** 本システムが担うのは表示制御のみ

### アーカイブ

**年度単位。** 先生の明示操作で運営動線からアーカイブへ移し、**解除もできる**（2026-07-26）。

- 導線は「**年度 → 作品名**」の 2 階層（2026-07-24）
- 検索対象は基本メタデータ（年度・チーム名・作品名・資料種別）＋概要の構造化データ（本文・使用技術欄）
- 導入前の歴代作品の**遡及投入はしない**。今年度からの自然蓄積
- **未決**：アーカイブ済み作品への**新規コメント投稿の可否**（後輩 → 歴代作品。卒業生は返信できず一方通行になる）

## 7. 全体を貫く設計原則

> **状態遷移（公開・当日進行・年度アーカイブ）は先生の明示操作を正とし、時刻・条件による自動遷移は持たない。**
> （2026-07-26。公開ボタン・手動進行・年度アーカイブの 3 決着からの帰納）

ER・API への含意はひとつ。**バッチ・スケジューラを設計に入れない。**

あわせて次の 2 つも設計を通じて効く。

- **実体レス**：ファイルの実体は保管せず、メタデータ（リンク・種別・提出状態）のみを管理する（2026-07-17）。アップロード UI は 1 つも存在しない
- **データ保持は無期限・削除機能を持たない**（2026-07-26）。論理削除も不要
