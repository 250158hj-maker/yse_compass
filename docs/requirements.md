## 3. 機能要件

> [!note] 記述方法
> - 企画書 §5-2 の「〜できる」を起点に、各機能を **①できること ②できないこと（境界）③受け入れ基準（どうなったら完成か・検証可能な形）** で再記述する

> **設計原則（2026-07-26・T11 で言語化）**
> **状態遷移（公開・当日進行・年度アーカイブ）は先生の明示操作を正とし、時刻・条件による自動遷移は持たない。**
> （§3-3 公開ボタン・§3-10 手動進行・§3-7 年度アーカイブの 3 決着からの帰納）
> ER・API への含意はひとつ — **バッチ・スケジューラを設計に入れない。**

### 3-1. 発表会資料管理機能 → 登録・閲覧

- **起点**：企画書 §5-2
- **できること**
  - 先生は「年度を開始」する操作で、歴代運用に準拠した 4 発表会（企画／設計／試作／最終＋定番の資料枠構成）の骨組みを一括生成できる（年度一括セットアップが「作成」の正規入口・2026-07-24）
  - 生成後、各発表会の日程・資料枠（種類・締切）は個別に編集できる — 発表会はコードに焼き込む固定データではなく運用データ
  - 発表会は回種別（企画／設計／試作／最終）を持つ。種別は固定 4 種・順序つきの列挙として構造化する
  - 先生は発表会に資料枠を定義できる。資料枠は **種類・締切・必須／任意** を持ち、テンプレートへの参照（リンク・任意）を持たせられる
  - 生徒には資料枠が「何をいつまでに準備すべきか」（提出対象・締切・必須か任意か）として表示される
- **できないこと**
  - テンプレートの強制・フォーマット崩れの検知や修正は扱わない — 当面の目標は「テンプレートへ簡単にアクセスできる」導線まで（それ以上を担うかは `open-questions.md` #7）
  - 4 種以外の発表会種別の追加・任意個数の個別新規作成は持たない — 型を崩す柔軟性はあえて排除し、使いやすさ（歴代運用への完全準拠）を優先。定番構成は歴代固定＝**コード定義**で持ち、プリセット管理 UI は作らない
- **受け入れ基準**
  - 先生が発表会を作成すると資料枠（種類・締切・必須／任意）が定義され、生徒側に提出対象として表示される。締切超過の提出は遅延として可視化される
  - 資料枠にテンプレ参照が設定されている場合、生徒は発表会詳細・提出画面からテンプレートへ 1 クリックで到達できる
  - 先生が年度セットアップを実行すると、4 回分の発表会が定番の資料枠つきで生成され、それぞれ個別編集できる
- **定番の資料枠の種類**（2026-08-18 ヒヤリング回答で判明。2026-07-24 の保留は解除）
  - 概要（現行呼称：概要集）／プレゼン資料／概要設計書／詳細設計書／試作品一式／完成作品一式
  - **概要（枠）は 4 発表会すべてにある**（各発表会に 1 件＝1 チーム年 4 件）
  - 4 発表会それぞれへの割り当ては `hearing.md` §7-2 に転記済み（2026-09-04・要旨）。逐語の現物との照合は水戸のタスクとして残る
- **確定（2026-09-04）**：提出方式は概要枠のみフォーム入力・他はリンク登録（H-2 決着・§3-3）／資料枠名は「概要」で生成物「概要集」と区別（H-1 決着）
- **確定（2026-09-04・H-9 決着）**：年度セットアップとチーム登録は**独立した操作**で、順序を強制しない。チームが 0 件のときの提出状況一覧は空状態を表示する

### 3-2. 提出状況一覧確認機能

- **起点**：企画書 §5-2
- **できること**
  - 先生は発表会ごとに「チーム × 資料枠」のマトリクスで提出状況を確認できる。未提出が一目で分かる
  - 提出状態は「未提出／提出済み」の **2 値**。提出済みには提出日時が併記され、締切超過の提出は遅延として表示される — **遅延は第 3 の状態ではなく、提出日時と締切の比較による導出表示**（2 値決定の維持・2026-07-26）
  - 締切・未提出の可視化はシステム内表示で行う（ホーム・発表会詳細・本一覧の強調表示）
- **できないこと**
  - 「リンクはあるが開けない」等の権限状態を状態値として持たない — 開ける状態の保証は提出フロー側の責務（`open-questions.md` #10）
  - 未提出者への通知送信（メール・プッシュ等）はしない — 通知基盤を持たない（2026-07-24）
- **受け入れ基準**
  - 先生が発表会を選ぶと全チーム × 全資料枠の一覧が表示され、各セルが「未提出／提出済み（＋提出日時・締切超過なら遅延識別）」を示す
  - 生徒が提出フォームを完了した時点で「提出済み」になる（＝完了定義）
- **未決**
  - **差し替えによって期限内提出が遅延に化ける** → `open-questions.md` **H-6**（ER 直結・本節の受け入れ基準の正しさに直結）

### 3-3. 資料公開・配信機能

- **起点**：企画書 §5-2
- **できること**
  - 先生は発表会単位で提出資料を生徒へ一括公開できる。公開は先生の明示操作（公開ボタン）で行い、公開前の資料は聴く生徒に表示されない（2026-07-26）
  - 発表する生徒は**概要**を構造化フォームで入力・提出する。入力欄は評価観点（`hearing.md` §7-4：背景・動機／起・結／1 ページ集約）を焼き込んだ設計とする。概要枠はリンク登録ではなくフォーム入力（§3-4 の唯一の例外）
  - 先生は入力済みの概要をシステム定義の統一レイアウトで概要ページ化し、**発表順**（§3-10 が源）に束ねた**概要集**を PDF として生成できる
  - 概要集はいつでも・何度でも生成できる（発表順変更・概要差し替えに追従）。未提出チームがある場合は生成時に警告し、先生が了承すればスキップして生成する
- **できないこと**
  - 概要ファイル（Word / Google ドキュメント等）の取り込み・変換・レイアウト補正はしない — ファイルを預かって直すのではなく、**入力の構造化で崩れ問題を根治する**（`hearing.md` §7-2）
  - 概要のレイアウトはシステムが定義する 1 種類のみ（コード定義・レイアウト編集 UI は作らない）。生徒によるフォント・レイアウトのカスタマイズはできない — **統一レイアウトが、先生の調整作業を消滅させる機構そのもの**
  - 画像対応（レベル 3）は当面持たない — 保留（捨てる判断はしない・2026-07-26）
- **受け入れ基準**
  - 全チームの概要提出後、先生が概要集を生成すると、発表順に並んだ統一レイアウトの概要集 PDF が得られ、**内容を確認・修正せずそのまま配布（コピー）できる**
  - 未提出チームがある状態で生成すると警告が表示され、先生が了承した場合は当該チームをスキップして生成される
  - チームが概要フォームを提出すると、提出状況一覧（§3-2）に「提出済み」として反映される
  - 先生が公開操作をすると、聴く生徒は発表会詳細・発表詳細から資料に到達できる。公開前は表示されない
- **確定（2026-09-04・K3 決着）**：概要集 PDF の生成手段は**サーバーサイド生成**（純粋 JS の PDF ライブラリ。ヘッドレスブラウザは使わない）。ライブラリの銘柄は実装着手時に確定（`decisions.md`／`design/05-output.md` 5-4）
- **保留**（`open-questions.md` §6 に一覧）
  - 画像対応（レベル 3）／概要フォームの入力項目と統一レイアウトの具体
- **未決**
  - 締切のソフトデッドライン化と生成タイミングの関係 → **H-7**
  - 発表順の変更による公開済み概要集の陳腐化 → **H-8**

### 3-4. 資料提出・差し替え機能

- **起点**：企画書 §5-2
- **できること**
  - 発表する生徒は自チームの資料枠に対して完成版を提出できる。形式（Canva / PPTX / Google スライド等）に依存しない（§1-1 の帰結）
  - 何度でも差し替えできる。差し替えは**上書き**で、システムは常に最新版のみを指す
  - 締切を超過しても提出・差し替えできる。締切超過の提出は遅延として可視化される（**締切はソフトデッドライン**・2026-07-26。Google Classroom の遅延提出と同型）
  - 提出フォームは URL の**形式検証**を行う（予防の下限）
- **できないこと**
  - 版履歴の保持・過去版の閲覧 — 制作過程の版管理は Drive 側の機能に委ねる。本システムの蓄積対象は最終成果物＋発表会でのフィードバック（コメント）
  - 年度アーカイブ後の提出・差し替え — 差し替えの終端は年度アーカイブ（§3-7 の先生の明示操作）
  - リンクの**アクセス可否**の検証はしない — システムと先生でアクセス文脈が異なり技術的に不確実。リハーサル段階の確認運用で回避し、#10 採用時に Drive API で再判断
- **受け入れ基準**
  - 生徒が提出を完了すると「提出済み」となり、提出状況一覧（§3-2）に反映される
  - 締切超過の提出・差し替えは、提出状況一覧（§3-2）で遅延として識別できる
  - 年度アーカイブ済みの提出物は編集できない
- **未決**
  - 提出の具体フロー（リンク登録フォームか、Drive 配置の自動化か）→ **#10**。**モック・API は Stage 1（リンク登録）で先行する**
  - 差し替えによる遅延判定の破綻 → **H-6**
  - 同一資料枠に Drive 配置と外部 URL 登録が混在する構図 → **H-13**（#10 の項に統合）

### 3-5. 発表資料閲覧機能

- **起点**：企画書 §5-2
- **できること**
  - 公開された資料をメタデータ（チーム・種別・発表会・提出日時）と共に確認し、リンク先（Drive 等）へ別タブで遷移して閲覧できる
  - 閲覧の入口は「発表詳細（チーム × 発表会）」画面 — チームの全資料リンクとコメント欄（§3-9）を 1 画面に集約する
- **できないこと**
  - システム内のネイティブプレビュー（Office 文書等のレンダリング）— §1-1 の帰結。実装コストに対して価値が薄い
- **受け入れ基準**
  - 聴く生徒は公開済み資料の一覧から発表詳細を開き、1 クリックでリンク先の資料を別タブで開ける
  - 公開前の資料はアプリ上に表示されない（本機能の表示制御はアプリ内導線の範囲。実体側のアクセス制御は #10 の決着に依存）
- **未決**

### 3-7. 資料のアーカイブ・検索機能

- **起点**：企画書 §5-2
- **できること**
  - 先生は「年度をアーカイブする」明示操作で、当該年度を運営動線からアーカイブへ移せる。誤操作に備え、**解除（取り消し）もできる**（自動遷移はしない — 設計原則）
  - 生徒・先生はアーカイブを「**年度 → 作品名**」で辿り、公開許可のある作品の概要・資料リンク・コメントを閲覧できる
  - キーワードで検索できる。検索対象は基本メタデータ（年度・チーム名・作品名・資料種別）＋概要の構造化データ（本文・**使用技術欄**）— 「Next.js で検索 → 該当プロジェクト一覧」の技術起点の探索が成立する
  - 卒業年度のチーム代表者（リーダー）は、全発表会終了後に作品の公開許可を設定できる。先生は設定状況を確認でき、代理設定・訂正もできる
- **できないこと**
  - Drive 実体（ファイル本文）の検索はしない（§1-1 の帰結）
  - 独立したタグ機能（タグ付与 UI・統制語彙の管理）は作らない — 技術情報の SSoT は概要フォームの使用技術欄（二重管理の回避）
  - リンク切れ（Drive 側の削除・権限変更）の自動検知・修復はしない — **Drive 運用マニュアル**（ヒヤリング後に作成する運用成果物）で実体側の安定を担保する
  - 公開許可のない作品はアーカイブ・検索結果に表示されない（既定＝非表示）
  - システム導入前の歴代作品の遡及投入はしない — アーカイブは今年度からの自然蓄積。**充実に年数を要することは先生と期待値合わせ**（ヒヤリング伝達事項）
- **受け入れ基準**
  - 先生が年度をアーカイブすると、当該年度がアーカイブの「年度 → 作品名」導線に載り、発表会一覧から外れる。解除で元に戻る
  - キーワード検索で、概要の使用技術・本文にマッチする公開許可済み作品が一覧される
  - 公開許可が未設定・拒否の作品は、アーカイブにも検索結果にも表示されない
  - チーム代表者が公開許可を設定すると、当該作品がアーカイブで閲覧可能になる
- **未決**
  - **検索が何の粒度を返すのか**（作品か発表か）→ **H-4**
  - アーカイブ済み作品への新規コメント投稿の可否 → `open-questions.md` §6
  - 使用技術欄の表記ゆれ対策 → **T-3**

  - **クラスは年度セットアップで生成する運用データ**で、登録主体は先生。クラス名は**分解せず文字列 1 つ**で持つ（H-3 決着）
  - **年度セットアップとチーム登録は独立した操作**で、順序を強制しない（H-9 決着）
  - **リーダーはチームの属性**（代表者 1 名への参照）で、責務は**公開許可の設定のみ**。チーム作成時に先生が指定し、以後変更できる
- **確定している事実**（2026-08-18・2026-08-19 ヒヤリング回答）
  - チーム編成は 2 年次 1 学期に決定し、現在はスプレッドシートで管理されている
  - クラスは **AI21 / BD21 / GS21 / IG21 / IG22** の 5 つ。命名は「学科＋学年＋組」（`IG21` ＝ IG 科 2 年 1 組）
  - リーダー（チーム代表者）概念が ER に必要なことは確定（2026-07-26・公開許可の同意者として）

### 3-9. コメント・フィードバック機能

- **起点**：企画書 §5-2（ラベル・いいねは確定分として継承）
- **できること**
  - 聴く生徒は公開された**発表（チーム × 発表会）**にコメントを投稿し、ラベル（感想・批評・その他）を付与できる。ラベルで絞り込める
  - 発表チームの生徒はコメントに返信して議論できる。**先生もコメント・返信を投稿できる**（議論の参加者）
  - 発表・コメントにいいねできる
  - コメント・いいねのアンカーは**発表単位** — 差し替え・リンク変更で対象がずれない（2026-07-24）
  - 投稿は**実名**（学校アカウントのフルネーム）で表示される — 先生依頼「責任ある発言」を顧客要件として採用（`hearing.md` §7-6・§4）
- **できないこと**
  - リアルタイム同期はしない — 新着コメントの反映は再読み込み・再取得時（**ライブ感よりコメントが蓄積されていることそのものが本質**）
  - 匿名・ニックネームでの投稿はできない（§4 の原則）
- **受け入れ基準**
  - 聴く生徒がコメント＋ラベルを投稿すると、発表詳細のコメント欄に実名つきで表示され、ラベルで絞り込める
  - 発表チームの返信がスレッドとして辿れる。発表・コメントのいいね数が表示される
  - 新着の反映はリアルタイムでなくてよい（再読み込みで反映されれば受け入れ）
- **未決**
  - 投稿者自身の編集・削除、先生による削除（モデレーション）の要否 → **T-2**。**モックで「…」メニューを描くか否かが、この未決に決着を迫る**

### 3-10. 当日タイムテーブル・進行管理機能

- **起点**：未決#2 の決着（2026-07-24。`hearing.md` §7-1 の手作業課題への応答）
- **できること**
  - 先生は発表会の**発表順と時刻枠**（開始時刻・所要・休憩）を編集し、タイムテーブルとして表示できる
  - 先生は当日「いま発表中のチーム」を手動で切り替えられ、タイムテーブル上で強調表示される
  - 生徒は自チームの発表順・時刻と全体の進行を確認できる
  - **発表順は概要集生成（§3-3）の並び順の源になる**
- **できないこと**
  - 時刻連動の自動進行はしない — 当日の押し・順番変更には先生の手動操作で追従する（**人間の判断が正**）
  - 進行操作（発表中の切り替え・順番変更）は先生のみ。生徒は閲覧のみ
- **受け入れ基準**
  - 先生がタイムテーブルを編集すると、生徒は発表会詳細側から発表順・時刻を確認できる
  - 先生が「発表中」を切り替えると、タイムテーブル表示で当該チームが強調される
- **確定（2026-09-04・#4 決着）**：進行状態・タイムテーブル変更の生徒画面への伝播方式は**ポーリング**。**間隔の値のみ未定**（`open-questions.md` §6 保留）
- **確定（2026-09-04・H-5 決着）**：発表順の決定操作は本節（タイムテーブル編集）に属する。並び替えが発表順の決定であり、専用の別画面は設けない。発表順は発表エンティティの整数属性として持つ

## 4. 非機能要件

> [!note]
> 企画書に存在しない層。各項目は**根拠とセットで**定義する。

### セキュリティ

- **確定**：アプリ実行ホスティングをしない（§1-1）
- **確定（2026-07-24）**：個人情報（氏名・学年）の原則 — 校内で既知かつ成果物（プレゼン資料・概要集）への氏名掲載がルール化されている情報であり、システム内の表示は**実名**を使用する。匿名化機能は持たない（実体資料に氏名が載る以上、システム側だけの匿名化は実効性がない）。前提は学内限定・一般公開なし（§1-1）。歴代アーカイブでも実名を維持する
- **TODO**：認可（ロール別アクセス制御）の原則 → 前提として `open-questions.md` **H-10**（ロールの解決方法）の決着が要る

### 性能

- **確定（2026-08-19 ヒヤリング分析。記録は 2026-08-30）**：発表会当日の**同時アクセス規模は 120 名**を前提とする
  - 根拠：現行の発表会の実運用規模。全校ではなく学年規模
  - 帰結：#4（当日進行の伝播方式）は 2026-09-04 に**ポーリングで決着**（`decisions.md`）。**間隔の値は未定** — 許容遅延が正典に無いため（→ `open-questions.md` **G-3**・§6 保留）

### データ保持・アーカイブ

- **確定（2026-07-26）**：保持期間は**無期限。削除機能を持たない** — 根拠：蓄積の実現が目的（企画書 §1）であり、保持するのはメタデータ＋概要テキストのみで容量増分が小さい（§1-1 実体レスの利点）。**論理削除も不要**
- **確定（2026-07-26）**：リンク切れ検知はシステムで持たない。**Drive 運用マニュアル**（ヒヤリング後に作成する運用成果物）で実体側の安定を担保 — 根拠：権限つきリンクの死活判定は技術的に不確実で実装コスト大
- **確定（2026-07-26）**：年度繰越は先生の明示操作「年度をアーカイブ」（可逆）で行う（§3-7・設計原則）

### 権利・運用

- **確定（2026-07-26）**：卒業生の公開許可 — 単位は**作品**（チーム × 年度）・同意者は**チーム代表者（リーダー）**・時期は**全発表会終了後**（在校中に取り切る）・既定は**非表示**。代表者がシステム内で設定し、先生が状況確認・代理設定できる（§3-7）。根拠：「一部の資料だけでは蓄積にならない」・先生の全員確認は非現実的
- **確定（2026-07-26）**：公開許可は「**アーカイブでの表示**」に対する同意であり、**データ削除請求の手段ではない** — 実体は学内 Drive にあり、削除の運用は学校の Drive 管理に属する。本システムが担うのは表示制御のみ
