## 1. ロールと動線

`requirements.md` §3-6（ログイン・ロール管理）は TODO のままだが、§3 各項の主語から次の3つの立場が読める。

| 記号 | 立場 | 性質 |
| --- | --- | --- |
| T | 先生 | 運営と**状態遷移の実行主体**（公開・当日進行・年度アーカイブ・年度セットアップ） |
| S1 | 発表する生徒 | 自チームの提出・概要入力・コメント返信 |
| S2 | 聴く生徒 | 閲覧・コメント投稿・いいね |

> **重要**：S1 / S2 はアカウントのロールではなく、**「その発表が自チームか否か」で決まる文脈**である。ロール（DBが持つ値）は「先生／生徒」の2値で足り、S1/S2 の出し分けは所属チームとの照合で行う。ここを混同すると認可設計が肥大する（→ `glossary.md` ユーザーとロール）。
> 先生ロールの親子二層構造（`open-questions.md` #8）は本書では**単層前提**。二層化した場合の影響は SC-20 に注記。

### 動線（ロール別の主要フロー）

- **T（年度運営）**：年度管理で一括セットアップ → 発表会編集で日程・締切を調整 → 提出状況一覧で回収を監視 → タイムテーブル編集 → 発表会詳細で公開 → 当日進行 → 概要集生成 → 年度アーカイブ
- **S1（提出）**：ホームで締切を確認 → 発表会詳細 → 資料提出フォーム／概要入力フォーム
- **S2（聴講・議論）**：発表会詳細（公開後）→ 発表詳細でリンク先へ遷移＋コメント
- **全員（蓄積の参照）**：アーカイブ → 年度 → 作品詳細／キーワード検索

## 2. 画面設計に効く要件（前提の確認）

モックを描く前に、次の5点は画面の形を直接規定する。

1. **状態遷移は先生の明示操作を正とし、時刻・条件による自動遷移は持たない**（`requirements.md` §3 冒頭の設計原則）
   → 公開・当日進行・年度アーカイブには、必ず**それを押す画面と押す人**が要る。自動化で画面を省略できない
2. **実体レス**（§1-1）
   → **ファイルアップロードUIは1つも存在しない**。すべてリンク登録＋外部タブ遷移
3. **コメント・いいねのアンカーは発表（チーム × 発表会）単位**（§3-9）
   → 議論の器は SC-12 発表詳細ただ1つ。資料ごとのコメント欄は作らない
4. **締切はソフトデッドライン**（2026-07-26 変更）
   → 提出UIに**ブロックは存在しない**。代わりに「遅延バッジ」の表示仕様が全提出系画面に要る
5. **概要枠だけはリンク登録ではなくフォーム入力**（§3-3・§3-4 の唯一の例外）
   → 資料枠の提出UIは2種類（SC-09 リンク登録 / SC-10 概要フォーム）に分岐する
   → ただし**どの枠がどちらかを決める属性は未決**（`open-questions.md` H-2）

## 4. 画面別 機能一覧

### SC-01 ログイン

- **要件**：§3-6
- **できること**
  - 学校 Google アカウント（Workspace）でのサインイン
  - 未ログイン時の全画面ガード（リダイレクト）
- **未決**：OAuth の実現可否は `requirements.md` §5 の最大の技術リスク。加えて**サインイン後のロール解決が未定義**（`open-questions.md` H-10）
- **メモ**：認証方式が未確定でも**この画面の見た目は変わらない**。技術リスクと切り離して先に確定できる唯一の画面

### SC-02 ホーム（ダッシュボード）

- **要件**：§3-2（締切・未提出の可視化）、§3-10（進行の確認）
- **できること（S1/S2）**
  - 自チームが提出すべき資料枠と締切の一覧（未提出・遅延を強調）
  - 直近の発表会への導線
  - 開催中の発表会があれば「いま発表中のチーム」の表示
- **できること（T）**
  - 当年度の発表会サマリ（提出率・締切間近・未提出の残数）
  - 年度セットアップ／公開／アーカイブ操作への導線
- **メモ**：**通知送信を持たない**（2026-07-24 決定）以上、締切の可視化はこの画面が最後の砦。「未提出の強調」を第一級の情報として扱う

### SC-03 発表会一覧（当年度）

- **要件**：§3-1、§3-7（発表会一覧は当年度の運営動線に徹する）
- **できること**
  - 当年度の4発表会（企画／設計／試作／最終）を**種別の順序**で表示
  - 各件の日程・締切・公開状態・提出状況サマリ
  - 発表会詳細への遷移
- **できないこと**
  - 任意個数・任意種別の発表会の新規作成（§3-1）→ **「＋新規作成」ボタンを置かない**
  - 過年度の表示（アーカイブへ分離・§3-7）

### SC-04 発表会詳細【ハブ】

- **要件**：§3-1 / §3-2 / §3-3 / §3-5 / §3-10
- **できること（共通）**
  - 発表会の概要（種別・日程・締切・公開状態）
  - 資料枠の一覧（種類・締切・**必須／任意**・テンプレート参照）→ **テンプレートへ1クリック到達**（§3-1 受け入れ基準）
  - タイムテーブルへの導線（§3-10）
  - 公開済みなら発表（チーム）一覧 → 発表詳細への遷移（§3-5）
- **できること（S1 追加）**
  - 自チームの枠ごとの提出状況（未提出／提出済み＋日時／遅延）
  - 提出フォーム・概要フォームへの導線
- **できること（T 追加）**
  - **【公開】ボタン**（発表会単位の一括公開・§3-3）／公開解除
  - 提出状況一覧・発表会編集・概要集生成への導線
- **できないこと**：チーム単位の公開出し分け（2026-07-26 決定）
- **メモ**：運営の中心。**ロール差分が最大の画面**でモックは3パターン要る

### SC-05 発表会編集（T）

- **要件**：§3-1
- **できること**
  - 日程・名称の編集
  - 資料枠の追加・編集・削除（種類・締切・**必須／任意**・テンプレート参照リンク）
- **できないこと**
  - 発表会そのものの新規作成（正規入口は SC-19 年度セットアップ）
  - 種別（企画／設計／試作／最終）の変更・追加 → **固定4種の表示のみ**
  - テンプレートのプリセット管理UI（コード定義で持つ）
- **参照**：定番の資料枠の種類は `requirements.md` §3-1 で確定済み（概要集／プレゼン資料／概要設計書／詳細設計書／試作品一式／完成作品一式）。**ただし4発表会それぞれへの割り当ては `hearing.md` §7-2 のとおり未転記**

### SC-06 提出状況一覧（マトリクス・T）

- **要件**：§3-2
- **できること**
  - **チーム × 資料枠のマトリクス**表示。未提出が一目で分かる
  - セルの状態：未提出／提出済み（提出日時併記）＋締切超過なら遅延識別
  - 未提出のフィルタ・強調
  - セルから提出物のリンク先へ遷移
- **できないこと**
  - 「リンクはあるが開けない」等の権限状態の保持（2値を崩さない）
  - 未提出者への通知送信（通知基盤なし）
- **メモ**：遅延は**第3の状態ではなく導出表示**。UIも「提出済みバッジ＋遅延マーク」の二層で表現し、3値に見えるデザインにしない
- **未決**：**差し替えで期限内提出が遅延に化ける**（`open-questions.md` H-6）。この画面の正しさに直結する

### SC-07 タイムテーブル（表示・当日進行）

- **要件**：§3-10
- **できること（共通）**
  - 発表順・開始時刻・所要・休憩の一覧表示
  - **「発表中」チームの強調表示**
  - 自チームの発表順・時刻のハイライト（生徒）
- **できること（T 追加）**
  - 「発表中」の手動切り替え
- **できないこと**：時刻連動の自動進行／生徒による進行操作
- **未決#4（伝播方式）**：**モックへの影響は「更新ボタンの有無」だけ**。手動リロード前提で描き、決着後に外す判断で先行できる。同時アクセス120名が確定したため**ポーリングで決着する見込み**
- **未決#5（2タブUX）**：Google Meet 併用が前提 → **狭幅でも読める縦長レイアウト**が要件になりうる画面

### SC-08 タイムテーブル編集（T）

- **要件**：§3-10
- **できること**
  - 発表順の並び替え
  - 開始時刻・所要時間の設定、休憩枠の挿入
- **メモ**：発表順は**概要集の並び順の源**（§3-3）。画面上に「概要集はこの順で生成されます」の注記を置くと、順序変更漏れによる運用事故を防げる
- **未決**：**そもそも発表順を誰がいつ決めるのかが要件に無い**（`open-questions.md` H-5）。この画面が「順序の決定」を担うのか、進行だけを担うのかが未確定

### SC-09 資料提出フォーム（S1）

- **要件**：§3-4
- **できること**
  - 対象資料枠の表示（種類・締切・必須／任意・テンプレートリンク）
  - **リンク（URL）の入力・保存＝提出**
  - URL の形式検証（2026-07-26 決定）
  - 何度でも差し替え（**上書き**・常に最新版のみ）
  - 締切超過時は「遅延として記録される」旨の警告表示（**ブロックはしない**）
- **できないこと**
  - ファイルアップロード（実体レス）／版履歴・過去版の閲覧
  - リンクのアクセス可否の検証
  - 年度アーカイブ後の編集（読み取り専用化）
- **未決#10（Drive統合）**：Stage 1＝リンク登録でモックを先行。自動化採用時はこの画面の中身が最も変わる

### SC-10 概要入力フォーム（S1）

- **要件**：§3-3
- **できること**
  - **構造化フォーム**入力。項目に `hearing.md` §7-4 の評価観点を焼き込む（背景・動機／起・結／1ページ集約／使用技術）
  - 統一レイアウトでのプレビュー
  - 提出 → 提出状況一覧（§3-2）に「提出済み」として反映
- **できないこと**
  - Word / Google ドキュメントの取り込み・変換
  - フォント・レイアウトのカスタマイズ（統一レイアウトは1種類のみ）
  - 画像の添付（レベル3・保留）
- **保留**：入力項目と統一レイアウトの具体（現行フォーマットの現物入手待ち）→ モックは §7-4 から仮置き
- **メモ**：**使用技術欄はアーカイブ検索の対象**（§3-7）＝独立タグ機能の代替。ここが検索体験の品質を決める（表記ゆれ対策は `open-questions.md` T-3）
- **語彙の注意**：この画面で提出するのは「**概要**」であって「概要集」ではない（`glossary.md` §5・`open-questions.md` H-1）

### SC-11 概要集生成・プレビュー（T）

- **要件**：§3-3
- **できること**
  - 発表順（§3-10 由来）に束ねた概要集のプレビュー
  - 未提出チームがある場合の**警告 → 了承でスキップして生成**
  - PDF の生成・ダウンロード。いつでも何度でも再生成できる
- **できないこと**：レイアウト編集UI／内容の手修正
- **保留**：PDF生成の実現手段（サーバー生成 or 印刷用ビュー＋ブラウザ印刷）→ 受け入れ基準は手段を縛らない。モックは印刷プレビュー相当で可
- **メモ**：ゴール像は「全員の提出が確認できたら、先生が**内容を知らなくてもすぐ配布できる**」。**手を入れる余地のあるUIを置いた時点で目的を外す**
- **未決**：生成後に遅れて提出が届いた場合・発表順が変わった場合の再生成の扱い（`open-questions.md` H-7・H-8）

### SC-12 発表詳細（チーム × 発表会）【議論の器】

- **要件**：§3-5 / §3-9
- **できること**
  - チーム名・作品名・メンバー（`hearing.md` §7-5「作品からチーム・所属者を辿れない」への応答）
  - 提出資料のリンク一覧（種別・提出日時）→ **別タブで開く**
  - 概要の表示
  - コメント投稿（**実名**）・ラベル付与（感想／批評／その他）・ラベルでの絞り込み
  - 返信スレッド（発表チーム・**先生も参加**）
  - 発表・コメントへのいいね
- **できないこと**
  - システム内プレビュー（Office文書のレンダリング）
  - 匿名・ニックネーム投稿
  - リアルタイム同期（再読み込みで反映されれば受け入れ）
  - 公開前の表示（S2には見えない）
- **未決**：投稿者自身の編集・削除、先生によるモデレーション（`open-questions.md` T-2）→ **モックで「…」メニューを描くか否かが、この未決に決着を迫る**
- **メモ**：アンカーが発表単位である以上、**コメントの入口はこの画面だけ**

### SC-14 チーム詳細

- **要件**：§3-8 / §3-7（公開許可）
- **できること**
